# Ядро магазина цифровых товаров (тестовое задание)

Бэкенд-ядро площадки цифровых товаров: заказы по SKU, приём вебхуков оплаты,
автоматическая выдача кода/ключа из заглушек-поставщиков. Всё построено вокруг
**однократной выдачи** (exactly-once), **корректной обработки таймаутов** и
**восстановления** зависших заказов.

- **Стек:** Python 3.13, FastAPI, PostgreSQL 17 (asyncpg), yoyo-migrations,
  фоновые задачи на asyncio + DB-очередь (outbox). Зависимости через `uv`.
- **Запуск:** Docker Compose (Postgres + приложение + сервис поставщиков + миграции).

Все состязательные сценарии из критериев приёмки закрыты автотестами
(`tests/`, 21 тест).

---

### Прогон тестов

Тесты идут по «живому» стеку (поднятому `make up`) и проверяют все сценарии
приёмки. Нужен только `uv` на хосте:

```bash
make test          # uv run --group dev pytest -v
```

Ожидаемый результат - `21 passed`. Если стек не поднят, тесты аккуратно
скипаются с подсказкой.

## Как воспроизвести проверки

### 1. Гонки: 50 параллельных вебхуков «оплачено» → ровно одна выдача

Тем же скриптом, что эмулирует платёжку:

```bash
# создать заказ, выстрелить 50 параллельных вебхуков, дождаться результата
uv run python scripts/emulate_payment.py demo --count 50
# -> fired 50 parallel webhooks -> {'200:applied': 1, '200:ignored': 49}
# -> final order: {'status': 'delivered', 'code': '...', 'supplier': 'A'}
```

- Ровно **один** вебхук перевёл заказ в `paid` (`applied: 1`), остальные - no-op.
- Итог - один код, один факт выдачи (`deliveries` содержит ровно одну строку).

Повторный вебхук с тем же `event_id` (идемпотентность):

```bash
ORDER=$(uv run python scripts/emulate_payment.py order --sku KEY-CS2-PRIME | python -c "import sys,ast;print(ast.literal_eval(sys.stdin.read())['id'])")
uv run python scripts/emulate_payment.py race --order $ORDER --count 50 --same-event
# -> {'200:applied': 1, '200:duplicate': 49}
```

Автотесты: `tests/test_concurrency.py`.

### 2. Отказ поставщика и fallback A → B


```bash
curl -sX POST localhost:8002/A/config -H 'content-type: application/json' -d '{"mode":"always_error"}'
curl -sX POST localhost:8002/B/config -H 'content-type: application/json' -d '{"mode":"normal"}'

ORDER=$(uv run python scripts/emulate_payment.py order --sku KEY-GTA5 | python -c "import sys,ast;print(ast.literal_eval(sys.stdin.read())['id'])")
uv run python scripts/emulate_payment.py pay --order $ORDER
uv run python scripts/emulate_payment.py get --order $ORDER
# -> status=delivered, supplier=B   (A выдал 0 кодов, B - ровно 1)
```

Автотест: `tests/test_fallback.py`.

### 3. Ловушка таймаута: поставщик успел выдать, но ответ не дошёл

```bash
# A выдаёт код и «зависает» дольше клиентского таймаута; B умышленно ломаем,
# чтобы неверный fallback провалил бы проверку.
curl -sX POST localhost:8002/A/config -d '{"mode":"always_timeout","timeout_delay_sec":8}' -H 'content-type: application/json'
curl -sX POST localhost:8002/B/config -d '{"mode":"always_error"}' -H 'content-type: application/json'

ORDER=$(uv run python scripts/emulate_payment.py order --sku KEY-EFT | python -c "import sys,ast;print(ast.literal_eval(sys.stdin.read())['id'])")
uv run python scripts/emulate_payment.py pay --order $ORDER
uv run python scripts/emulate_payment.py get --order $ORDER
# -> status=delivered, supplier=A;  A.issued увеличился ровно на 1 (нет двойной выдачи)
```

Повтор идёт с **тем же** `request_id`, поэтому поставщик возвращает **тот же**
код, а не выдаёт новый. Автотест: `tests/test_supplier_timeout.py`.

### 4. Невыдаваемый товар → честный возврат (терминал без краха)

```bash
curl -sX POST localhost:8002/A/config -d '{"mode":"always_oos"}' -H 'content-type: application/json'
curl -sX POST localhost:8002/B/config -d '{"mode":"always_oos"}' -H 'content-type: application/json'
# оплатить заказ -> ни один поставщик не может выдать -> строка возвращается,
# заказ уходит в refunded без падения; по деньгам оплачено == возвращено.
curl -sX POST localhost:8001/admin/reconcile   # money_mismatch: [], ledger.balanced: true
```

Автотесты: `tests/test_out_of_stock_recovery.py` (полный возврат),
`tests/test_multi_item.py` (частичная выдача + возврат в одном заказе).

### 5. Как проверить, что деньги сходятся

```bash
make reconcile
# {"paid_not_delivered":[...], "delivered_not_paid":[], "money_mismatch":[],
#  "ledger":{"balanced":true, "total_debit":X, "total_credit":X}}
```

- `ledger.balanced` - двойная запись: `sum(debit) == sum(credit)` **всегда**.
- `money_mismatch` - терминальные заказы, где нарушено `оплачено = выдано +
  возвращено` (в норме **пуст**): по каждому заказу счёт-обязательство
  `customer_funds` обнуляется, когда все строки терминальны.
- `delivered_not_paid` - выдача без оплаты (должно быть **пусто**).

Итоги за период считаются из **append-only истории** и сходятся двумя
независимыми путями (обороты за период vs остатки as-of):

```bash
curl -s "localhost:8001/admin/report?from_ts=2020-01-01T00:00:00Z&to_ts=2100-01-01T00:00:00Z"
# -> {"double_entry_balanced":true, "consistent":true,
#     "payments":P, "revenue":R, "refunds":F}      # выполняется P == R + F
```

Состояние денег и заказа на **любой прошлый момент** восстанавливается из истории:
`GET /admin/ledger/at?ts=...`, `GET /admin/orders/{id}/at?ts=...`.
Автотесты: `tests/test_core.py` (баланс), `tests/test_history.py` (as-of + период).

### 6. Каталог под нагрузкой (Stage 5): план запроса витрины

```bash
make load          # зальёт ~5000 SKU и покажет EXPLAIN (ANALYZE, BUFFERS)
```

### 7. Частичный сбой заказа (мультитовар): выданное остаётся, за невыданное - возврат

Заказ из нескольких SKU; каждая строка выдаётся своим поставщиком независимо.
Часть строк может не выдаться - тогда выданные остаются у покупателя, за
невыданные возвращаются деньги, заказ завершается `partially_delivered`.

```bash
# мультитоварный заказ (по одной штуке на позицию)
ORDER=$(curl -sX POST localhost:8001/orders -H 'content-type: application/json' \
  -d '{"items":["KEY-CS2-PRIME","KEY-GTA5"]}' \
  | python -c "import sys,json;print(json.load(sys.stdin)['id'])")
uv run python scripts/emulate_payment.py pay --order $ORDER
curl -s localhost:8001/orders/$ORDER
# -> status: delivered | partially_delivered | refunded;
#    items[].status: delivered/refunded, у выданных - items[].code
```

Полностью **воспроизводимый** частичный сбой (у поставщиков ровно один код на две
строки → одна выдаётся, одна возвращается) - автотест
`tests/test_multi_item.py::test_partial_delivery_and_refund`. По деньгам при этом
`оплачено = выдано + возвращено` (см. п.5).

### 8. Недобросовестный поставщик: дубль/чужой код и «ошибка, но код выдал»

Ответу `/issue` доверять нельзя - корректность держим сами (см. «Ключевые
решения → Недоверенный поставщик»).

**Чужой/дублирующий код отвергается, покупатель получает свой:**

```bash
# 1) выдать заказ честно (поставщик A) и запомнить его код C
# 2) заставить A отдавать уже кому-то выданный код:
curl -sX POST localhost:8002/A/config -d '{"mode":"foreign_code"}' -H 'content-type: application/json'
# 3) новый оплаченный заказ: A присылает C -> отвергнут (UNIQUE(supplier,code)) ->
#    fallback на B, покупатель получает СВОЙ код; C не уходит во второй заказ.
curl -s localhost:8001/admin/integrity     # зафиксированное расхождение видно здесь
```

**«Ошибка, но код выдан» - повтор без второй выдачи и без ошибочного fallback:**

```bash
curl -sX POST localhost:8002/A/config -d '{"mode":"error_but_issue"}' -H 'content-type: application/json'
curl -sX POST localhost:8002/B/config -d '{"mode":"always_error"}'    -H 'content-type: application/json'
# оплатить заказ: A резервирует код и отвечает 500; повтор ТЕМ ЖЕ request_id
# возвращает тот же код -> выдан A ровно один раз (GET /A/status: issued +1, B - 0).
```

Утёкшие коды (выдал, но ответ потерян) подбирает фоновая автосверка -
`POST /admin/integrity/audit`, открытые расхождения - `GET /admin/integrity`.
Автотесты: `tests/test_untrusted_supplier.py`.

## Модель данных

| Таблица | Назначение | Ключевые гарантии |
|---|---|---|
| `products`, `stock` | каталог + денормализованный счётчик остатка | «горячий» запрос витрины O(1) на строку |
| `orders` | заказ-агрегат; статус производный от строк | статусный переход под блокировкой строки |
| `order_items` | строка заказа (свой SKU, цена, поставщик, жизненный цикл) | независимый терминал `delivered`/`refunded` на строку |
| `webhook_events` | инбокс вебхуков (at-least-once) | `event_id` PK → дедуп |
| `deliveries` | выданный код, привязанный к **строке** | `item_id` PK + UNIQUE(supplier, code) → **не более одной выдачи на строку** |
| `delivery_outbox` | DB-очередь фоновой выдачи, задача **на строку** | claim через `FOR UPDATE SKIP LOCKED` |
| `ledger_entries` | двойная запись движений денег (cash/customer_funds/revenue/refunds) | `sum(debit) == sum(credit)` всегда; customer_funds заказа → 0 в терминале |
| `supplier_inventory`, `supplier_issues`, `supplier_config` | заглушки поставщиков | идемпотентность по `request_id`, инъекция отказов |
| `supplier_discrepancies` | журнал расхождений с недоверенным поставщиком | автосверка находит и по возможности чинит (реклейм утёкших кодов) |
| `supplier_rate_limit` | общий счётчик фиксированного окна на поставщика | атомарный токен под блокировкой строки → лимит не превышается всеми воркерами |
| `order_events` | append-only лог переходов состояний | триггер запрещает UPDATE/DELETE → историю не переписать; реконструкция состояния на любой момент |

Статусы строки: `created → paid → delivering → delivered`, ветка `refunded`
(не удалось выдать → деньги назад). Статус заказа - производный: `delivered`
(все строки выданы), `partially_delivered` (часть выдана, часть возвращена),
`refunded` (все возвращены), плюс `payment_failed` (финальный).

**Мультитоварный заказ (Этап 6).** В одном заказе несколько строк, каждая
выдаётся своим поставщиком независимо (`request_id = "{item_id}:{supplier}"`).
Гранулярность exactly-once перенесена с заказа на строку: `deliveries` и
`delivery_outbox` ключуются по `item_id`, строки ретраятся и восстанавливаются
поодиночке. Что смогли выдать - остаётся у покупателя; за строку, которую
детерминированно не выдал ни один поставщик (все дали `out_of_stock`/`5xx`),
оформляется честный возврат. Деньги считаются на трёх счетах, поэтому всегда
`оплачено = выдано + возвращено`: оплата кредитует `customer_funds` на сумму
заказа, каждая выдача дебетует его на цену строки в `revenue`, каждый возврат -
в `refunds`; когда все строки терминальны, `customer_funds` заказа обнуляется.
`GET /admin/reconcile` возвращает список `money_mismatch` - терминальные заказы,
где это равенство нарушено (в норме пуст). Все шаги идемпотентны и доводят заказ
до терминала после аварийного рестарта в середине выдачи.

**Недоверенный поставщик (Этап 7).** Ответу `/issue` доверять нельзя: поставщик
может молча выдать один код дважды, отдать чужой код или ответить ошибкой, уже
выдав код. Мы гарантируем корректность сами:
- *Один код - один заказ.* Код доверяется только после **атомарной привязки**:
  `UNIQUE(supplier, code)` + трёхзначный результат `bound / already_bound /
  code_conflict`. На `code_conflict` (дубль/чужой код) строка НЕ помечается
  выданной - пишем расхождение и делаем fallback на другого поставщика; исчерпали
  всех → честный возврат. Пустую строку «выданной» больше не пометить.
- *Ошибка ≠ «код не выдан».* Перед fallback сверяемся с **аудит-каналом**
  поставщика (`GET /{s}/issue/{request_id}` - надёжный, в отличие от боевого
  `/issue`): если код по нашему `request_id` уже есть - привязываем его, второй
  выдачи нет. `request_id = {item_id}:{supplier}` стабилен.
- *Автосверка без ручного вмешательства.* Фоновый `IntegrityWorker` периодически
  тянет `GET /{s}/issues` и сверяет с нашими `deliveries`: привязывает утёкшие
  коды (поставщик выдал, мы не записали), а дубли/чужие коды/рассинхрон/«возвращено,
  но выдано» фиксирует в `supplier_discrepancies`. Открытые расхождения -
  `GET /admin/integrity`, принудительный прогон - `POST /admin/integrity/audit`.

Византийское поведение заглушки включается конфигом: `duplicate_code`,
`foreign_code`, `error_but_issue`.

**Лимит поставщика / бэкпрешер (Этап 8).** У поставщика ограничение на число
запросов в окне, а заказы приходят пачками. Перед каждым вызовом `/issue` берём
токен из **общего счётчика фиксированного окна** (`supplier_rate_limit`,
атомарно под `FOR UPDATE` → лимит соблюдают все воркеры/процессы сразу). Нет
токена - это не сбой: задача остаётся в durable-очереди `delivery_outbox` и
откладывается на короткий интервал (`defer`, без роста экспоненты и без
инкремента `attempts`), пока не освободится окно. Значит **ничего не теряется и
лимит не превышается**. Возврат из-за нехватки ёмкости не делается - только из-за
детерминированного отказа всех поставщиков. **Оплаченные раньше неоплаченных:** в
очередь выдачи попадают только оплаченные строки (код выдаётся лишь после оплаты),
неоплаченные ёмкость не тратят; среди оплаченных - FIFO по времени постановки.
Прогресс виден в `GET /admin/queue` (в очереди / выдано / возвращено /
неоплаченные + расход токенов по поставщикам); лимит задаётся
`POST /admin/rate-limit/{A|B}`.

**История и темпоральность (Этап 9).** По append-only логам восстанавливаем
точное состояние на любой прошлый момент. Источники истины: `order_events`
(переходы состояний - order_created / payment_received / item_delivered /
item_refunded / …) и `ledger_entries` (деньги, двойная запись, timestamped);
изменяемые `orders`/`order_items` - лишь быстрая проекция «текущего». Событие
пишется в **той же транзакции**, что и guarded-переход, поэтому ровно один раз.
- *Состояние на дату:* `GET /admin/orders/{id}/at?ts=...` сворачивает события с
  `occurred_at <= ts`, `GET /admin/ledger/at?ts=...` суммирует проводки с
  `created_at <= ts`.
- *Только дополняется:* UPDATE/DELETE на `order_events` и `ledger_entries`
  запрещены триггером БД - задним числом ничего не переписать.
- *Итоги за период:* `GET /admin/report?from_ts=..&to_ts=..` считает обороты и
  сверяет их с остатками as-of (два независимых пути дают один ответ:
  `closing == opening + movement`), плюс `оплачено = выдано + возвращено`.

## Ключевые решения

**Exactly-once по оплате (Этап 2).** Две независимые линии обороны:
1. *Дедуп инбокса* - `INSERT INTO webhook_events(event_id) ON CONFLICT DO NOTHING`.
   Работу делает только первое появление конкретного `event_id`; повторы - no-op
   (критерий 2).
2. *Переход под защитой состояния* - `UPDATE orders SET status='paid'
   WHERE status='created'` под блокировкой строки. Из N параллельных вебхуков по
   одному заказу ровно один меняет состояние и ставит задачу на выдачу; остальные -
   no-op (критерий 1). Задача выдачи ставится в **той же транзакции** (паттерн
   outbox) - оплаченный заказ не может остаться без задачи на выдачу.

Вебхук «раньше заказа» (критерий 3): событие всегда сохраняется; если заказа ещё
нет - остаётся `processed=false` и применяется свипером/`/admin/recover`, когда
заказ появится.

**Exactly-once по выдаче (Этапы 1, 3, 6).** Три замка (гранулярность - строка):
- claim задачи из `delivery_outbox` через `FOR UPDATE SKIP LOCKED` → один воркер
  на строку;
- `deliveries.item_id` PRIMARY KEY → максимум один код на строку;
- идемпотентность поставщика по `request_id` → повтор возвращает тот же код.

**Ловушка таймаута (Этап 3) - главное.** `request_id` **стабилен** для пары
(строка, поставщик): `f"{item_id}:{supplier}"`. Отсюда правило:
`таймаут ≠ отказ`. При таймауте поставщик мог успеть выдать код, поэтому мы
**никогда не делаем fallback по таймауту** - повторяем **тот же** `request_id`
(сначала в рамках вызова, затем фоново), и получаем уже выданный код. Fallback на
B делается только при **детерминированном** отрицании A (`out_of_stock` или
`5xx`/недоступность) - по контракту это значит, что код не выдавался. Заглушка
моделирует ровно эту ситуацию: в режиме `always_timeout` она сначала фиксирует
выдачу в БД (commit), и только потом «висит» - так что ответ теряется, а код уже
существует.

**Наблюдаемость и восстановление (Этап 4).** Структурированные (JSON) события на
всех денежных/выдачных переходах («Заказ создан», «Оплата проведена», «Товар
выдан», «Таймаут поставщика, повтор того же request_id», …) с корреляцией по
`order_id/event_id/request_id/supplier`. Эндпоинт `GET /admin/reconcile` даёт
срез «оплачен-не-выдан» / «выдан-не-оплачен» и проверку баланса журнала. Фоновый
recovery-воркер: применяет отложенные вебхуки, переклеймивает застрявшие в
`processing` задачи (упавший воркер) и переставляет восстановимые заказы. Всё
идемпотентно - восстановление физически не может привести к двойной выдаче.

**Каталог под нагрузкой (Этап 5).** Остаток хранится денормализованным счётчиком
`stock.available` (а не `COUNT(*)` по кодам), поэтому цена строки не зависит от
объёма пула. Частичный индекс `products (type, sku) WHERE is_active` обслуживает
`WHERE is_active ORDER BY type, sku LIMIT N`: Postgres идёт по индексу по порядку
и останавливается после N строк - без сортировки и без full scan. Факт на ~5000
SKU:

```
Limit (actual time=0.008..0.129 rows=50)
  -> Nested Loop Left Join
       -> Index Scan using products_storefront_idx on products  (rows=50)
       -> Index Scan using stock_pkey on stock  (loops=50)
Execution Time: 0.156 ms
```

## Как масштабировали бы под нагрузку

- **Партиционирование** `orders`/`webhook_events`/`ledger_entries` по времени;
  холодные партиции - в архив.
- **Горизонтальное масштабирование воркеров** уже встроено: число воркеров
  выдачи/восстановления задаётся в `.env` (`DELIVERY_WORKER_COUNT` /
  `RECOVERY_WORKER_COUNT`) - они делят один stateless-набор сервисов и
  конкурентно разбирают очередь через `FOR UPDATE SKIP LOCKED` (один заказ не
  берут два воркера, двойной выдачи нет). Это же масштабируется и на несколько
  процессов/подов без изменений кода. При большом числе воркеров не забыть
  поднять размер пула БД (`POSTGRES.pool_max_size`).
- **Витрина остатков** под реальный трафик - кэш (Redis) с инвалидацией по
  событию `stock.changed`, либо материализованное представление; сама SQL-схема
  уже готова к этому.
- **Разнесение доменов**: сервис поставщиков вынесен отдельным процессом (в
  реальном мире - своя БД и свой деплой); платёжный инбокс можно вынести в
  брокер (Kafka/SQS) с тем же принципом дедупа по `event_id`.
- **Backpressure/ретраи** по выдаче - экспоненциальный бэкофф уже реализован в
  outbox; при устойчивых отказах поставщиков заказы безопасно «ждут» в
  восстановимом статусе.

## Структура

Слоение строгое: **вся SQL - только в repository**, в service - исключительно
бизнес-логика. Транзакции, охватывающие несколько запросов (exactly-once
переходы), реализованы через Unit-of-Work (`repository/postgresql/uow.py`):
service открывает границу транзакции и передаёт соединение в методы репозиториев,
а сами SQL-запросы живут в репозиториях.

```
app/                      # приложение-магазин (слои: routes → services → repository)
  internal/services/      # order/payment/delivery/reconcile/catalog - только бизнес-логика
  internal/workers/       # delivery_worker (очередь), recovery_worker (свипер)
  internal/repository/    # доступ к БД (asyncpg): вся SQL + uow.py (Unit of Work)
  pkg/clients/            # HTTP-клиент к поставщикам (классификация таймаут/ошибка)
  pkg/logger/events.py    # структурированные JSON-события
supplier/                 # заглушки поставщиков A/B (идемпотентность + инъекция отказов)
migrations/               # yoyo: схема + сид (каталог, 50 ключей, конфиг поставщиков)
scripts/emulate_payment.py# эмулятор платёжки + харнесс гонок
scripts/load_catalog.py   # Stage 5: нагрузка каталога + EXPLAIN
tests/                    # 21 тест (+ мультитовар, недоверенный поставщик, лимит, история)
```

## Фактически затраченное время

Примерная разбивка по этапам (≈ 2.5-3 рабочих дня суммарно):

| Этап | Содержание | ≈ время |
|---|---|---|
| Ядро (1-5) | exactly-once оплата/выдача, ловушка таймаута, восстановление, витрина | ≈ 1 день |
| Мультитовар (6) | строки заказа, частичная выдача + возврат, деньги на 3 счетах | ≈ 0.5 дня |
| Недоверенный поставщик (7) | атомарная привязка кода, verify-before-fallback, автосверка | ≈ 0.5 дня |
| Лимит/бэкпрешер (8) | общий счётчик окна, приоритет очереди, метрики прогресса | ≈ 0.25 дня |
| История (9) | append-only лог, реконструкция as-of, итоги за период | ≈ 0.25 дня |

Основное время - проектирование модели данных и инвариантов (exactly-once,
сходимость денег, идемпотентность при повторах и сбоях) и тесты на критичных
путях; сама реализация по слоям (routes → services → repository) прямолинейна.
